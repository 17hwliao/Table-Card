## 确认的缺陷

### 1. [P1] Windows PowerShell 5.1 无法解析当前启动和加入脚本

- 位置：`start-table-card.ps1:1`、`join-table-card.ps1:1`；`start-table-card.bat:4` 调用 `powershell.exe`。
- 触发：使用桌面入口或 BAT，让 Windows PowerShell 5.1 读取含中文的无 BOM UTF-8 脚本。
- 原因：两个文件已没有 UTF-8 BOM。本机 Windows PowerShell 5.1 按本地代码页读取，中文内容被误解码并产生语法错误。
- 影响：启动链路在执行前失败，服务端/客户端不能由这些入口正常开启。
- 实证：13 个 PowerShell 脚本在 PowerShell 7 中解析通过；同批脚本在 Windows PowerShell 5.1 中，启动脚本有 12 个解析错误、加入脚本有 6 个，其余 11 个通过。实际运行 `scripts/test-launchers.ps1` 也在启动前失败。
- 最小修正：恢复这两个脚本的 UTF-8 BOM；保留 Windows PowerShell 5.1 解析和真实入口启动检查。
- 证据：`runtime/review-20261013/parse-win51.jsonl`、`launchers-original.txt`。

### 2. [P2] 宝可梦唯一可用招式被封锁时无法推进回合

- 位置：`internal/pokemon/battle.go:30`、`internal/pokemon/duel.go:101`。
- 触发：只有一个可用招式的伙伴被 Disable 封锁；没有可换伙伴，且战斗不能逃跑、没有可用道具。例如低等级凯西只会瞬间移动。
- 原因：离线和玩家对战入口都在执行战斗前拒绝被封锁的招式。封锁倒计时只在战斗执行中递减；底层已有无可用招式时的挣扎逻辑，但入口使它不可达。
- 影响：无法以技能推进回合，无法等待封锁自然解除；训练家战可能卡住，玩家对战可能拖至超时。
- 实证：`TestReviewOnlyDisabledMoveCanAdvanceBattle` 的离线和在线场景均失败。
- 最小修正：根据所有可用招式决定是否进入挣扎/强制回合；不要要求选择不存在的其他招式。

### 3. [P2] 玩家对战的蓄力释放被错误的 PP 检查拦截

- 位置：`internal/pokemon/duel.go:98`；离线对应校验在 `internal/pokemon/battle.go:27`。
- 触发：日光束等蓄力招式在上一回合消耗最后一点 PP，当前正在释放，同时另一个招式还有 PP。
- 原因：玩家对战提交端检查所选槽 PP 为零时直接拒绝，没有像离线分支一样排除已记录的蓄力释放/连续行动。
- 影响：按正确蓄力槽提交会报“该技能PP耗尽”。选择其他有 PP 的槽可绕过检查并释放已记录招式，因此不是所有这类对局都会彻底锁死，但正常提示和操作不一致。
- 实证：`TestReviewDuelChargeWithOtherPP` 失败；没有其他 PP 时的对照测试 `TestReviewDuelReleasesLastPPCharge` 通过。
- 最小修正：离线和玩家对战使用一致的强制行动校验，释放阶段不再次要求所选槽有 PP。

### 4. [P2] 瞬间移动等结束野战后残留战斗临时状态

- 位置：`internal/pokemon/combat_attack.go:277–280`；下一场入口 `internal/pokemon/game.go:299`。
- 触发：野战中已有能力变化、替身等临时效果，通过 `SWITCH_AND_TELEPORT_EFFECT` 退出。
- 原因：该分支只清空 `g.Battle`，没有像普通逃跑分支那样清理队伍的 `Combat`；下一场 `startBattle` 也不清理这些状态。
- 影响：只应存在于一场战斗内的能力变化、替身等可带到下一场，影响伤害和行动。
- 实证：`TestReviewTeleportClearsTemporaryCombat` 成功退出战斗，但发现临时状态仍非零，测试失败。
- 最小修正：统一战斗退出清理，清除全队战斗临时状态；保留持久状态的既有规则。

### 5. [P2] 终端总宽度超界，草坪窄窗口帮助文字也未适配

- 位置：`internal/terminal/app/app.go:804`、`:834`、`:937–943`。
- 触发：120/160 列开启在线侧栏，或 60 列显示草坪接力。
- 原因：侧栏预算只扣 2 列分隔符，实际 `" │ "` 占 3 列；草坪共用标题、状态和帮助文字没有按剩余宽度换行/裁剪。
- 影响：宽窗口整帧超过终端 1 列；60 列场景出现 71 列行，可能截断或换行。真实终端换行对鼠标坐标的具体影响尚未实机验证。
- 实证：`TestReviewGardenFrameFitsTerminal` 在上述尺寸失败；80/90 列通过。独立草坪控制器的卡片/格子鼠标几何测试通过，说明不能只检查控制器局部布局。
- 最小修正：完整计入分隔符宽度，并约束共用标题/提示行；验收整个 View 的每行宽度及渲染位置对应的鼠标命中。

### 6. [P2] 同一身份可同时进入多个房间，在线状态和房间聊天归属不确定

- 位置：`internal/server/server.go:142`、`:280`；快速匹配 `internal/server/lifecycle.go:282`、`:298`；归属计算 `internal/server/social.go:277`、`:287`。
- 触发：同一有效身份连续创建多个房间，或创建后加入/匹配另一个房间。
- 原因：创建、加入和匹配没有在操作锁内统一检查该身份已有的真人座位。社交通道虽限制同身份会话，房间成员关系仍可重复。
- 影响：房间聊天取遍历到的首个房间，在线状态则按相同身份覆盖；结果依赖映射遍历顺序，可显示错误模式/房间、将房间消息送至错误房间。
- 实证：真实 HTTP 请求中同一有效身份两次创建房间均返回 201；`TestReviewSingleIdentityCannotOccupyMultipleRooms` 失败。加入和匹配路径缺同类检查由静态调用链确认，未分别建立 HTTP 复现测试。
- 最小修正：在共享操作锁内统一保证真人身份只有一个有效房间归属；切换前明确离开或接管旧座位。

### 7. [P2] 并发首次加载身份会读取未写完的文件

- 位置：`internal/terminal/profile/profile.go:44–51`；首次读取 `:26`。
- 触发：多个客户端同时首次使用同一服务器地址/昵称。
- 原因：`O_EXCL` 创建后文件已可见，JSON 还未写完；其他调用会读取空文件或部分内容，立即当作损坏，或在创建冲突后立即读取。
- 影响：正常创建中的身份被报成“身份文件无法解析”，部分客户端启动失败。这是文件发布时序问题，不是 Go 内存数据竞争。
- 实证：`TestReviewConcurrentFirstIdentityLoad` 使用 16 个并发调用，最多 30 组首次昵称，在常规和竞态测试中均复现失败。
- 最小修正：跨进程协调并完整发布身份文件，或对明确处于创建过程的读取作有界等待；仍应保留真实损坏文件，不可用覆盖重建掩盖问题。
